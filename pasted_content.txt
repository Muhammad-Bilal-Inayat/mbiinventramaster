## 1. Server-side features

### 1.1 Startup, hosting & build — `server.ts`, `server.js`, `app.js`, `package.json`, `scripts/`
- Production entry is `app.js` → `server.js`, which auto-builds if `dist/` is missing or stale (built SHA ≠ source SHA) and then loads `dist/server.cjs` (built from `server.ts`).
- Dev entry is `tsx watch server.ts`; build is `vite build` (client) + `esbuild server.ts` (server bundle) + a build-SHA stamp script.
- Listens on `PORT` env or `3000` by default, with response compression and 100 MB JSON/body limits.
- Central data directory resolver (`server/lib/dataDir.ts`) — all tenant data lives under `DATA_DIR` (pinned to `/home/<domain>/mbi_data` on the host), never inside a release folder; legacy release data is migrated, never overwritten.
- Pre-deploy backup script (`scripts/predeploy-backup.cjs`) and a build-SHA stamp script (`scripts/stamp-build-sha.cjs`).

### 1.2 Health & status — `server.ts`, `server/routes/versionRoutes.ts`
- API health endpoint reporting server + database status.
- Vault-engine health/status endpoint for the SQLite storage layer.
- Data health endpoint showing the live data directory + tenant count.
- Sync health/status endpoint.
- Version endpoint reporting the running build version.

### 1.3 Auth & sessions — `server/routes/authRoutes.ts`, `server/controllers/authController.ts`, `server/auth/jwt.ts`, `server/auth/password.ts`, `server/auth/totp.ts`
- Username/email/mobile + password login issuing a JWT, with device tracking.
- Google Sign-In (server-verified ID token) with automatic tenant provisioning.
- 10-day free trial registration (trial tenant provisioning with phone validation).
- Forgot-password via email OTP, and OTP verification + password reset.
- Token refresh and a rescue path that re-issues a session when refresh fails.
- Logout, and a separate master login for the Master panel.
- Post-login phone gate for phoneless tenant owners (phone save + duplicate check).
- Password policy enforced server-side (never trusted from the client alone).
- TOTP two-factor auth for both master and tenant accounts (setup / enable / disable / status / reset).
- Per-login audit events and login-attempt tracking.

### 1.4 Devices & hardware binding — `server/routes/licenseRoutes.ts`, `server/routes/deviceAccessRoutes.ts`, `server/db/sqliteVaultManager.ts`
- Licence-key validation that resolves the plan tier (Platinum/Enterprise → Platinum, Silver/Basic → Silver, anything else → Gold).
- Device binding to a licence, bound-device listing, primary-device auto-bind, and hardware-ID (HWID) reset.
- Licence countdown (trial/licence days-left and expiry) and licence status checks.
- Device unlock-key generation + verification, device access requests, and request review/status flow.
- Server-side device/user limit gates on every new bind and new user creation (see §3.1).

### 1.5 Tenants, licences & plans — `server/routes/tenantRoutes.ts`, `server/routes/licenseRoutes.ts`, `server/routes/fleetRoutes.ts`, `server/lib/planLimits.ts`, `server/lib/licenseCountdown.ts`, `server/lib/renewalOptions.ts`
- Tenant info, tenant data-key, tenant feature flags, and tenant UI settings (server-persisted).
- Tenant sub-user controls and per-tenant 2FA management.
- Licence creation, extension, plan change, and licence listing (master/fleet side).
- Plan limits enforced server-side: Silver 2 devices / 2 users, Gold 5 / 5, Platinum 15 / 15, with grandfathering (a stored higher ceiling is honoured as a frozen cap, never raised by the gates).
- Renewal options and licence countdown shared between server and client.
- Tenant maintenance mode, tenant lock toggle, and tenant delete/wipe (master side, destructive — needs explicit master action).

### 1.6 Sync & realtime — `server/routes/syncRoutes.ts`, `server/controllers/syncController.ts`, `server/lib/syncGuards.ts`, `server/lib/sseSanitizer.ts`
- Sync pull (server → device) and push (device → server), plus single-record push and record delete.
- Delta sync, batch sync, sync flush, sync diagnostics, sync logs, and connection-pool stats.
- Server-Sent Events (SSE) live broadcast of tenant events, with sanitized payloads.
- Sync restore points (create / read) and manual sync triggers (all tenants or one tenant).
- Strict tenant isolation on pull: rows stamped with the JWT tenant; foreign-tenant rows are never served to the wrong tenant.
- Sync push guards (server-side validation of pushed records) and quarantine of contaminated records.
- Pull windows: invoices latest 500, purchases latest 200, party payments latest 500, shifts latest 50 (older records stay on the server but are not pulled to a fresh device).
- Sync is permanently additive: it never deletes local records.

### 1.7 Data storage, encryption & backups — `server/db/sqliteVaultManager.ts`, `server/db/tenantManager.ts`, `server/lib/tenantCrypto.ts`, `server/lib/legacyEncryptionKey.ts`, `server/lib/restorePoints.ts`, `server/services/tenantBackupService.ts`, `server/routes/backupRoutes.ts`
- Per-tenant SQLite vaults (`tenants/<id>/vault.sqlite`) plus a master hub database holding all tenants.
- Tenant data encrypted with AES-256-GCM using per-tenant derived keys; legacy encryption key kept decrypt-only for old data.

- Automatic restore points: on startup and before a new release is deployed (only restore points auto-expire; live data never auto-deletes).
- Per-tenant encrypted backup service: full vault dump to encrypted JSON, with push / download / delete backup endpoints.
- Tenant backup + restore endpoints, including backup listing and restore from backup.
- Master client backups directory for operator-level tenant backups.

## 3. Enterprise (Platinum) plan features — marked enterprise-only

> **Prices & limits:** Platinum = Rs 6,999/mo (1-year Rs 69,990; 3-year Rs 209,970; 5-year Rs 349,950) · 15 user accounts · 15 devices/terminals · 10 branches. Sources: `src/config/canonicalPlans.ts`, `server/lib/planLimits.ts`. Gold = 5 users / 5 devices / 5 branches; Silver = 2 / 2 / 2.

### 3.1 Server side — what the server enables/allows for Platinum tenants
- [ENTERPRISE] Device limit 15 and user-account limit 15 enforced on every new device bind and new user creation (`server/lib/planLimits.ts`, `server/routes/deviceAccessRoutes.ts`, `server/controllers/userController.ts`, `server/db/sqliteVaultManager.ts`).
- [ENTERPRISE] Grandfathering: a stored ceiling above the plan limit is honoured as a frozen cap and never raised by the gates; existing devices/users are never removed, unbound, or locked by plan enforcement.
- [ENTERPRISE] Fleet plan update maps enterprise → 15 for both max_devices and max_users (`server/routes/fleetRoutes.ts`).
- [ENTERPRISE] Role-override write for the tenant's own sub-users: Platinum tenant owners may set overrides for their own sub-users only; a master override, once set, can never be overwritten or removed by the tenant (`server/services/roleOverrideService.ts`, `server/routes/roleOverrideRoutes.ts` — non-Platinum write attempts get "Role customization is a Platinum feature").
- [ENTERPRISE] AI quota 300 questions/day (vs Gold 100, Silver 50, trial/guest 20), with optional master quota override (`server/services/aiAssistantService.ts`).
- [ENTERPRISE] WhatsApp Meta Cloud API service is labelled a Platinum plan feature (`server/services/whatsappMetaService.ts`); route-level plan enforcement on the WhatsApp routes was **(unverified)** — see §3.4.
- [ENTERPRISE] Licence-key validation maps PLAT/ENTERPRISE plan strings to the Platinum tier (`server/routes/licenseRoutes.ts`).

### 3.2 User side — what Platinum users get in the app
- [ENTERPRISE] Multi-godown / multi-warehouse management and inter-godown stock transfers (`src/utils/planPermissions.ts` module tiers: `godowns`, `multi_godowns`, `multi_warehouse`, `stock_transfer`, `godown_management`).
- [ENTERPRISE] FBR POS integration + digital fiscalization: tax-FBR, FBR POS, digital fiscal stamps, QR digital tax stamps, sales-tax invoicing, FBR tax audit reports.
- [ENTERPRISE] Double-entry accounting: chart of accounts, journal vouchers, trial balance, and consolidated financial audits.
- [ENTERPRISE] Online customer storefront + e-commerce: online storefront, web-orders manager, online promotions, digital product catalogue, online store sales/performance reports.
- [ENTERPRISE] Multi-branch HQ: multi-branch operations, inter-branch stock transfers + transfer approvals, centralized branch sync, consolidated chain analytics, multi-branch consolidated reports.
- [ENTERPRISE] Regulatory registers: narcotics register, controlled-drug register, and DRAP Form 8 register.
- [ENTERPRISE] Custom field-level permissions and custom field security.
- [ENTERPRISE] Lifetime extended data recovery (extended recycle-bin / recovery window).
- [ENTERPRISE] All 24 dashboard widgets (lower plans see a subset).
- [ENTERPRISE] Mesh sync (multi-branch mesh synchronization) and AI reorder velocity.
- [ENTERPRISE] Automated WhatsApp gateway (auto WhatsApp automation).
- [ENTERPRISE] 10 branches and 15 user accounts / 15 terminals (vs Gold 5 / 5, Silver 2 / 2).
- [ENTERPRISE] Full enterprise feature set in the plan dictionary (`src/lib/planFeatureManager.ts` PLAN_FEATURES.ENTERPRISE), which also includes the Gold-tier items by inheritance (bookers, prescriptions, audit trail — see note in §3.4).
- NOT Platinum (for contrast, to avoid confusion): bookers/field force, prescriptions + chronic refills, full audit trail, sale orders/quotations/estimates/challans, and the 180-day FEFO radar are Gold-and-above, not Platinum-only; FEFO 30/60/90 alerts, purchase orders, and core POS/inventory/parties are Silver (all plans).

### 3.3 Licence terms (Platinum)
- Monthly, 1-year, 3-year, and 5-year durations; every multi-year price is exactly monthly × 10 per year (2 free months per year, ~17% saving).
- Lifetime licences exist only in the master licence catalogue (no public equivalent): Silver Rs 120,000 · Gold Rs 250,000 · Platinum Rs 450,000 (values from the old master catalogue, carried into `src/config/canonicalPlans.ts` as `lifetime`).
- Short trial durations (2/7/15 days) exist only in the master licence catalogue; the public trial is the 10-day free trial.
- Licence expiry is enforced by the licence-countdown + licence-expiry middleware; expired licences fall back to restricted behaviour (exact restriction set **(unverified)** in the lines read).

### 3.4 Server/user gating mismatches — flagged plainly, not smoothed over
- **Most Platinum features are enforced client-side only.** The sidebar, module tiers (`src/utils/planPermissions.ts`), and route gates hide Platinum menus from Silver/Gold users, but the server does not re-check feature use on sync: sync accepts record types regardless of plan. Server-side enforcement is limited to device/user limits, role-override writes, AI quotas, and licence validation. A modified client could therefore sync Platinum-feature data that the server would store.
- **Unknown-plan defaults differ by endpoint.** Licence-key validation maps an unrecognised plan to Gold (`server/routes/licenseRoutes.ts`), while the plan-limits resolver returns null for unrecognised plans and its callers fall back to Basic limits (`server/lib/planLimits.ts` — fail-closed-Basic). Same tenant, different assumed tier depending on which endpoint runs.
- **Display fallbacks disagree with enforcement.** Fleet list fallbacks (`max_users || 5`, `max_devices || 3`), the tenant-column migration default (`max_devices DEFAULT 3`), and licence device-check fallbacks (`maxDevices = 10` when no licence record exists) all differ from the enforced 2/5/15 table. The plan-limits file itself documents these as display-only and never used by enforcement — but a reader of the fleet UI can still see the wrong numbers.
- **Provisioning history.** Old trial provisioning seeded max_users = 10 and max_devices = 1 for Basic trials (vs advertised 2/2); new trials are seeded 2/2. Legacy tenants may still carry the old stored values, honoured only as frozen ceilings under the grandfathering rule.
- **Branch vs device counts.** The catalogue's Platinum "10 branches" is a branch/firm count, not a device count (devices = 15). The plans config file explicitly warns not to confuse the two.
- **Enterprise feature list includes Gold items by design.** `PLAN_FEATURES.ENTERPRISE` accumulates BASIC + BUSINESS + ENTERPRISE keys, so bookers, prescriptions, and audit-trail keys appear in the enterprise list too. That is inheritance, not a second gating rule — but it means the enterprise list alone cannot be read as "Platinum-only".
- **WhatsApp gateway enforcement gap (unverified).** The auto-WhatsApp-gateway module key is Platinum in the client tiers and the Meta service header calls it a Platinum feature, but no plan check was found in `server/routes/whatsappRoutes.ts` itself. Whether the server blocks non-Platinum WhatsApp sends is not established from the code read.

## 4. Warranty logic (mandatory section)

> **Plain summary first:** In MBI Inventra, "warranty" is a **pharma drug-warranty certificate (Form 2-A under the Drug Act 1976)** — a formality document that accompanies a sale or purchase bill. It is **not** a product warranty: there is **no warranty duration, no expiry date, no expiry calculation, no claims workflow, and no claim status** anywhere in the current code. The 2026-10-18 redesign explicitly removed type/period/claim-contact fields from the bill warranty config.

### 4.1 Warranty features (one line each)
- Warranty toggle on the sale bill form, turning the bill into a warranty bill (`src/pages/SaleInvoicePage.tsx`).
- Warranty toggle on the purchase bill form, turning the bill into a warranty bill (`src/pages/PurchaseInvoicePage.tsx`).
- Warranty bill is a **separate formality document**: converting a sale into a warranty bill loads it as a NEW document with no ID/number, leaving the original sale untouched; converting back strips the warranty flags and loads it as a normal sale.
- Warranty fields on a bill: discount percentage (default 15%), NTN (TIN/NTN), and pharmacy licence number — licence + NTN are required when warranty is ON.
- Three print toggles on a warranty bill: header on/off, print on/off, footer on/off.
- Controlled-drug auto-off: warranty printing is automatically disabled when controlled-drug items are present on the bill.
- Pre-warranty item backup: turning warranty OFF restores the exact pre-warranty item list.
- Warranty Register report: all warranty bills (sale + purchase), tenant-isolated, with totals, total value, top party, and warranties-by-party, plus Excel export and print (`src/pages/Reports.tsx`, report id `warranty_register`, category "Warranty & Certificates").
- Warranty print settings: show/hide discount %, show/hide TIN/NTN, show/hide licence on the printed bill (`src/types/invoice.ts`, `src/components/sales/InvoicePrintModal.tsx`, `src/components/sales/PrintPreviewModal.tsx`, `src/components/invoice/InvoiceSettingsPanel.tsx`).
- Warranty columns on the printed bill: batch number and expiry columns are forced visible on warranty bills even when column config hides them.
- Warranty terms line printed on invoices: "Warranty claims require invoice copy" (default invoice terms, `src/services/authService.ts`).
- Warranty settings defaults: claim-contact display toggle + default claim contact (`support@mbiinventra.com / 0336-4585863`) in transaction settings (`src/contexts/SettingsContext.tsx`, `src/components/settings/TransactionTab.tsx`).
- Server print defaults for the master printer-templates panel: header "TAX & DRUG WARRANTY INVOICE", Form 2-A declaration text ("Under Section 23 of Drug Act 1976… medicines sold do not contravene any section of Drug Act 1976"), and a show-drug-warranty flag (`server/routes/adminMasterRoutes.ts`).
- Warranty plan gate: `warrantyManagement` permission key exists in the plan/permission files, and the purchase page applies an explicit plan gate (`isWarrantyAllowedForPlan`); the sale-page gate was **(unverified)** in the lines read.
- Warranty Register navigation entry under "Warranty & Certificates" (`src/pages/navigationMeta.ts`).

### 4.2 Warranty logic — short summary
- **Where recorded:** On the bill record itself, not on items and not on a separate warranty table. Sale invoices and purchase orders carry `isWarrantyBill?: boolean` + `warrantyDetails?: { discountPct, tinNtn, licenseNumber, isHeaderEnabled, isFooterEnabled, isPrintingEnabled, hasControlledDrug, controlledPrintEnabled }` (sale bills additionally allow `customerSignature`, `sellerSignature`, `shopStamp`, `customFields`) — `src/types.ts`.
- **Duration / expiry:** NONE. No duration field, no start/end date, no expiry calculation, and no expiry alert exists in current code. The redesign comment states it directly: "redesigned 2026-10-18: no type/period/claimContact" (`src/pages/SaleInvoicePage.tsx`). Any expiry shown on a warranty bill is the medicine batch expiry column, not a warranty expiry.
- **Claims / returns:** NO claims workflow. There is no claim record, claim status, claim approval, or claim-to-return linkage. The only claim-related text is the printed terms line ("Warranty claims require invoice copy") and the settings display field for a claim contact. Sale/purchase returns are separate flows and are not linked to warranty bills.
- **Sync:** NO dedicated warranty sync columns and NO warranty endpoint on the server. Warranty fields travel inside the bill record's JSON through the generic bill sync (invoices / purchases tables); nothing in `server/controllers/syncController.ts` or the client sync engine names a warranty column. (Verified by grep: zero `isWarrantyBill`/`warrantyDetails` matches in `server/` and in the client sync files.)
- **UI surfaces that show warranty info:** sale bill warranty panel, purchase bill warranty panel, invoice print modal + print preview, Reports → Warranty Register, settings TransactionTab + PrintTab, master printer-templates panel.
- **What is partial / absent (plainly):** duration/expiry — absent; claims tracking — absent; warranty-to-return linkage — absent; server-side warranty validation — absent (the server never checks warranty fields); sale-page plan gate — unverified. The warranty feature as built is a document + register + print feature, not a warranty-management system.
